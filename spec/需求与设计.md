## 二、用户三条使用需求与解法

### 需求 ① 手机上可视化清晰，不需要多余操作就能看到重要信息

| 设计动作 | 具体做法 |
|---|---|
| **首屏即答案** | 打开即见「今天要做」清单，不用点任何东西 |
| 信息按重要性分三层 | L1 首屏直出（待跟进 / 面试倒计时 / S 级新岗位）；L2 一屏滑完（岗位列表）；L3 需点击（详情、时间线、原始 JD） |
| 单列 · 大字号 | 手机端正文 12.5px、最小 11px；卡片单列铺满，不做横向滚动 |
| 底部四 Tab | 今日 / 岗位 / 投递 / 自荐信 —— 任一功能两步内可达 |
| PWA | 可"添加到手机桌面"，全屏无浏览器地址栏；断网可看（数据已内联） |
| 关键数字直出 | 在投 / 待跟进 / 面试中 三个数字始终在首屏顶部 |
| 逾期视觉优先 | 逾期待跟进项用强调色左边框，自动浮到"今天要做"最上面 |

### 需求 ② 岗位来源面广，保证精品多

**采集方式**：不逐个爬招聘站（反爬 + 合规风险 + 易失效），改用**站点限定检索**——按「岗位关键词 × 上海 × 站点」组合检索，一次覆盖 20+ 来源。

**来源清单（待用户增删）**

| 类别 | 来源 | 备注 |
|---|---|---|
| 综合平台 | 猎聘、BOSS直聘、智联招聘、前程无忧、拉勾 | 岗位量最大 |
| 应届/校招 | 应届生求职网、实习僧、牛客网、海投网 | 部分岗位接受往届 |
| 中小企业 | 全职招聘网、中国中小企业服务网 | 门槛较低，对非应届友好 |
| 上海本地 | 上海国资、张江人才、上海人才网、乐业上海（人社局） | 国企/事业单位，稳定性高 |
| AI 技术垂直 | V2EX 酷工作、掘金、即刻、机器之心、GitHub Jobs | 技术岗密度高、质量高 |
| 企业直招 | 目标公司官网/招聘页/公众号 | 跳过中介，信息最准 |
| 内推/猎头 | 猎聘顾问、脉脉 | 补充非公开岗位 |

**"精品"定义**（打分引擎的筛选口径）：技能栈重合度高 + 门槛可达（接受非应届/经验不限）+ 薪资 ≥ 12k + 上海 + 方向为 AI 应用/Agent/RAG。

### 需求 ③ 自荐信方便复制，只要 Top 岗的，减少 AI 使用

| 措施 | 说明 |
|---|---|
| **只对 S 级生成** | 阈值 ≥78 分（可调）；A/B/C 级不自动生成，需要时手动点 |
| **生成后缓存** | 自荐信文本写回 `applications.json` 的 `cover_letter` 字段，**永不重复生成** |
| **一键复制** | 卡片上直接有「复制自荐信」按钮，复制纯文本（无格式残留），粘到邮件/招聘站即可 |
| **模板化降本** | 自荐信 = 固定骨架（个人优势 / 项目证据 / 岗位匹配）+ 少量 JD 定制段 → 单封 token 消耗压到最低 |
| **数据不出本机** | 生成在本地跑（用户自己的 key），不经过第三方服务 |

## 三、AI 使用分层（成本控制核心）

| 环节 | 用 AI？ | 频率 | 说明 |
|---|---|---|---|
| 岗位采集 | **用**（检索） | **每天 1 次** | 唯一固定成本项 |
| 匹配打分 | **不用** | 无限次 | 纯规则关键词算法：命中技能词 + 门槛判断 + 来源/薪资加权。确定性、可测试、零成本 |
| 岗位排序 | 不用 | 无限次 | 读打分结果排序 |
| 自荐信 | **用** | 仅 S 级新建时 | 生成后缓存，重复打开不重复调用 |
| 页面渲染 | 不用 | 无限次 | 纯静态 |

**结论**：每天只有 1 次采集 + 偶尔几封自荐信会产生开销，其余全部零成本。

## 六、状态机

```
wishlist ──→ applied ──→ screening ──→ interview ──→ offer
 待投递       已投递       沟通中        面试中      Offer
                │            │             │
                └────────────┴─────────────┴──→ rejected / dropped / ghosted
```

| 状态 | 中文 | 进入条件 | 看板列 |
|---|---|---|---|
| `wishlist` | 待投递 | 已评估但未投 | ① 待投递 |
| `applied` | 已投递 | 简历已发出 | ② 已投递 |
| `screening` | 沟通中 | HR 已联系 / 约面 | ③ 沟通中 |
| `interview` | 面试中 | 已进面试流程 | ④ 面试中 |
| `offer` | Offer | 拿到 offer | ⑤ Offer |
| `rejected` | 被拒 | 对方拒绝 | ⑥ 已结束 |
| `dropped` | 已放弃 | 我主动放弃 | ⑥ 已结束 |
| `ghosted` | 无回应 | 投递超 14 天无回复 | ⑥ 已结束 |

**自动规则**：`applied` 且距今 > 14 天 → 标黄提示"是否转为无回应"。**不自动改状态**，状态变更必须用户确认。

## 七、技术方案

### 架构：离线优先 + 种子与补丁分离

```
多来源检索（每天 1 次，AI）
        ↓
data/seed-*.json          ←── 岗位池：只读，每天被采集脚本覆盖（公开）
        ↓
build.py 内联（seed + CSS + JS → 单文件）
        ↓
dist/index.html  ──→  GitHub Pages（零成本公网托管）
        ↓
localStorage              ←── 补丁层：你的操作记录（私有）
        ↓
   merge(seed, state)     ←── 渲染时合并，两者各写各的
        ↓
   导出 / 导入 JSON  ←→  丢回 data/state.json 重新构建，即得 Git 版本历史
```

**为什么不写后端**：数据量只有几十条，用不上数据库；无后端 = 零成本 + 零运维 + 零安全面。「无服务端架构 + 离线优先」本身是可写进简历的技术亮点。

### 存储模型（M2 核心决策）

**问题**：岗位池每天被采集脚本重写，投递进度是你手写的。两者存在同一份数据里，第二天采集一跑，进度就没了。

**解法**：拆成两层，各自独立演进。

| 层 | 存放 | 谁写 | 生命周期 |
|---|---|---|---|
| **种子 seed** | `data/seed-*.json`，构建期内联 | 采集脚本 | 每天覆盖 |
| **补丁 state** | 浏览器 localStorage | 你（界面操作） | 长期累积 |

补丁只存**改动过的字段**，按岗位 `id` 匹配：

```json
{
  "schema": 1,
  "updated_at": "2026-09-21T18:52",
  "patches": {
    "liaoning-xinxi-ae": {
      "status": "applied",
      "applied_at": "2026-09-21",
      "next_action": "等 HR 回复",
      "notes": "…",
      "timeline": [{ "at": "2026-09-21T18:52", "kind": "status",
                     "from": "wishlist", "to": "applied", "note": "" }]
    }
  },
  "added":   [ { "id": "manual-xxx", "...": "手动录入的完整岗位" } ],
  "removed": [ "已归档岗位的 id" ]
}
```

由此得到三条性质：

1. 重新采集岗位 → 进度不受影响
2. 岗位被采集脚本删掉 → 记录也不受影响（补丁还在）
3. 归档是**软删除**：`removed` 里记一笔，`added` 和 `patches` 原样保留，可完整恢复

**内嵌数据只在本地为空时采纳**：个人版会把 state 内嵌进 HTML；如果每次打开都采纳内嵌版本，
重新部署一次就把手机上的进度回滚了。所以规则是「localStorage 为空（首次打开 / 换新设备）才采纳」，
需要主动拉取时走「载入内嵌数据」。

### 三种构建，产物文件名刻意不同

| 命令 | 产物 | 用途 |
|---|---|---|
| `python build.py` | `dist/index.html` | 公开版，**不含任何个人数据** |
| `python build.py --demo` | `dist/preview-demo.html` | 演示版，虚构状态 |
| `python build.py --state data/state.json` | `dist/local.html` | 个人版，内嵌真实记录，**只能本地用** |

`--state` 若试图输出成 `index.html`，**构建直接报错退出**——对"真实数据被误发布"的物理护栏。

### 为什么必须有端到端测试

`python build.py` 只证明"能生成 HTML"，不证明"点得动、记得住"。M1 靠浏览器验证抓到过
「详情面板关不掉」；M2 的风险更高——**状态改了没存住、刷新就回滚、备注写丢**，这些只跑构建永远发现不了。

`tools/e2e.py` 的核心断言只有一条：**点完状态 → 刷新页面 → 数据还在吗。**

它必须在 `file://` 和 `http://` 两种环境下各跑一遍：这两个环境下 localStorage 的行为不一样，
不能想当然（实测两者都可用，但这是测出来的结论，不是假设）。

### 隐私说明

作品集仓库**必须公开**，但投递记录含公司名/薪资/面试情况，属个人隐私。

**默认方案（甲）**：公开仓库只放代码 + 种子示例数据；真实数据只存浏览器 localStorage，导出后自己留存。
内嵌个人数据的产物物理隔离在 `local.html`，构建脚本还有一道拒绝护栏。

**M2 实际交付**：8 状态流转（含结束态与撤销）、投递日期自动落库、跟进动作与日期、
备注 + 自动时间线 + 快捷「记一笔」、手动录入岗位、软删除归档与恢复、
复制/下载导出、文件/剪贴板导入（合并语义）、清空并自动备份。
测试 32 → 39 项，新增 `tools/e2e.py`（2 环境 × 25 项断言）。

**M3 实际交付**：`tools/gen_letter.py`（简历 + 岗位 → DeepSeek → `data/letters.json`，纯标准库
`urllib` 无新依赖）+ `tools/prompts/cover_letter.md`（11 条硬约束，独立成文件便于调文风）。
CLI：`--list / --dry-run / --job / --force / --show / --resume / --max-chars`。
3 个 S 级岗各生成一封（503–544 字），人工审稿通过：点名项目与算法、无套话、缺口一句。
构建层把 letters 合并进 `cover_letter`，但**可发布的 `index.html` 一律排除**——
按输出文件名自动判定，不依赖使用者记得加参数。测试 39 → 63 项。

**M3 踩到的两个坑**

1. **写进提示词的长度约束，模型并不遵守**。要求 450–550 字，实测输出 520–610 字（超出 20%~35%）；
   加一轮"压缩到 500 字"的兜底调用，也只收敛到 508–544。
   → 结论：字数这类硬约束必须**程序侧兜底**（超阈值就再压一轮），不能只写在提示词里指望模型自觉。
2. **数据层的错误会被自荐信如实放大**。复医天健的 `why_match` 写着"了解 Dify / Coze"，
   而简历里根本没有 → 首轮生成照抄成"接触过扣子这类平台的同类逻辑"。
   这**不是模型幻觉，是数据层错误被忠实复制**，比幻觉更隐蔽（看起来有理有据）。
   → 已加提示词第 11 条「技术名词白名单」（信里每个工具名都必须能在简历里找到，匹配点里的
   JD 加分项不得写成自己的经历）并重生成修复。
   → **待用户核实**：那条 `why_match` 本身是否成立（是否真的用过 Coze / Dify），
   若成立则简历该补，若不成立则种子数据要改。

**岗位采集的接入时机**：M1-M3 先用 09-17 的 17 个岗位跑通全链路，**采集自动化放 M4 之后**——避免在核心流程未验证前就引入不确定性。

**M4 实际交付**

| 文件 | 作用 |
|---|---|
| `src/manifest.webmanifest` | PWA 清单；`start_url` / `scope` / `id` 全部 `./` 相对写法（子路径部署必需） |
| `src/sw.js` | 预缓存 7 项 + network-first 导航 + cache-first 静态 + 版本化缓存 + 升级握手 |
| `src/icons/` | 4 张 PNG（192 / 512 / maskable-512 / apple-touch-icon-180），随仓库提交 |
| `tools/make_icons.py` | 用 Playwright 把 SVG 渲染成精确尺寸 PNG（不引入 Pillow 依赖） |
| `tools/check_public.py` | 发布闸门：白名单文件 + 内容泄漏 + PWA 资产完整性 |
| `tools/e2e_pwa.py` | 25 项断言：注册 → 接管 → 缓存 → 断网 → 时效性 → 升级链路 |
| `.github/workflows/deploy.yml` | 测试 → `build.py --publish` → 闸门 → Pages 部署（PR 不部署） |
| `build.py --publish` | 先清空目标目录，只产出 index.html + PWA 附属文件，且**从不读本地 state** |

产物结构变化：`dist-publish/` 是每次重建的干净目录，与本地开发用的 `dist/`
（混着 `preview-demo.html` 与 `local.html`）物理分开。理由是部署时若整目录上传，
含自荐信正文的演示版会一起公开；靠人记得删不如靠"每次重建"。

**PWA 与"单文件"的并存方式**：Service Worker 不能内联（浏览器强制同源独立文件），
所以 HTML 保持自包含（`file://` 双击可用、零外链），仅在托管时通过**相对路径引用**
额外挂上 manifest 与 sw.js。PWA 附属文件只随可发布的 `index.html` 产出；
运行时也用"页面有没有引用 manifest"做第二道判断，防止演示版/个人版与 index.html
争抢同一目录的 SW scope。

**三条关键取舍**

| 问题 | 选择 | 理由 |
|---|---|---|
| 导航缓存策略 | **network-first** | 每天更新岗位。cache-first 会让部署后手机永远停在旧数据且无从察觉 |
| 新版本接管时机 | 等用户点「刷新」 | `install` 里直接 `skipWaiting()` 会造成「新缓存配旧页面」的错配 |
| 缓存版本号来源 | 产物内容 sha1 前 10 位 | 用时间戳会让每次构建都弹「有新版本」，提示变噪音后就会被无视 |

**M4 踩到的坑**

1. **`statechange` 竞态**（实测抓到，且是真会漏到线上的 bug）。新 SW 安装可能快到
   等 `updatefound` 回调跑起来时状态已是 `installed`，那个 `statechange` 早错过了 ——
   表现是「新版本确实装上了，却永远不提示刷新」。测试诊断数据坐实了这点：
   `updatefound: 1` 但捕获到的 `statechange` 数为 `0`。
   → 修法：`updatefound` 回调里除了挂监听，还**主动查一次**当前状态。
2. **测试台的假故障**：`http.server` 的 `Last-Modified` 只有**秒**精度，而升级测试要在
   同一秒内连改两次 `sw.js`。第二次请求命中 `If-Modified-Since` 拿到 `304`，
   浏览器据此判定脚本未变、跳过安装，失败信息变成「没检测到新版本」。
   → 测试服务器显式丢弃 `If-Modified-Since`（模拟真实 CDN 的内容哈希 ETag）。
   → 顺带记一条真实的部署注意事项：**两次部署落在同一秒内，条件请求无法区分**。
3. **闸门规则写错自己**：最初把 `data/state.json` 列为禁止字符串，结果界面帮助文案里
   本来就有这个文件名，误报。→ 改成检查语义信号（`state_inlined` / `state_source=file:` /
   `cover_letter` 非空），而不是查名字。
4. **发布构建会读到本地 state**：`build.py --publish` 原本走默认路径解析，
   一旦本机存在 `data/state.json` 就会自动内联 → 随即被自己的护栏拒绝（构建失败）。
   → `--publish` 分支直接关掉状态读取，而不是依赖使用者记得别加参数。
5. **图标视觉**：`职` 底下的红杠与字形末横糊成一团，放大看像脏点 → 删掉，一个字足够。

**为什么采集不做成全自动抓取**（用户拍板：检索清单 + 粘贴录入）

| 方案 | 反爬风险 | 覆盖渠道 | 维护成本 |
|---|---|---|---|
| 全自动爬招聘站 | 高（BOSS / 猎聘有登录墙与风控） | 受限于爬得动的站 | 每次改版都要修 |
| **检索清单 + 规则解析（选定）** | **零**（只拼 URL，不抓页面） | **全部 23 个渠道** | **零**（单条链接失效不致命） |

**采集链路的三个设计点**

1. **域名缺失的渠道不留 `site:` 空查询**：张江人才、目标公司官网这类没有稳定搜索 URL 的渠道，
   检索式退回「渠道名 + 城市 + 关键词 + 招聘」，否则会生成 `site: 上海 AI应用开发` 这种废查询。
2. **认不出的字段留空并在报告里点名**，不猜也不填默认值 —— 猜错的公司名会污染之后所有投递记录。
   推荐用法是显式传 `--company / --title / --url`。
3. **「20+ 渠道」由测试守着**：`tools/channels.json` 少于 20 条直接测试失败，防止渠道被悄悄砍掉。

**M5 踩到的坑**

1. **`build.py` 把种子文件名写死**成 `seed-2026-09-17.json`，采集脚本产出新日期的种子根本接不上 ——
   设计文档写了「每天覆盖」、代码里却只认一份，典型脱节。→ 抽出 `src/seed_store.latest_seed()`，三处共用。
2. **公司名被截断**：非贪婪量词遇到「科技」就停，`上海某某智能科技有限公司` 变成 `上海某某智能科技`。
   → 分两级匹配：优先「…有限公司」全称，取不到再退回简称。
3. **`jd_text` 只用于打分，界面没有渲染** —— 而设计里「原始 JD」是详情层的内容。→ 详情面板补折叠区
   （`<details>`，默认收起，免得几百行正文把页面撑到翻不到底）。
4. **老测试会被采集动作搞红**：多处断言「17 个岗位」，一旦 `data/` 出现新 seed 就失败。
   → `tests/conftest.py` 把默认种子钉死；`build()` 的 `seed_path` 默认值改为运行时可覆盖。
